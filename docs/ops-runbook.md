# 运维手册（值班用）

拿到告警先查本页对应条目；处置写进工单 / 值班群并在后台留处理说明。告警码与处置条目由 `RunbookCoverageTest` 保证一一对应（新加告警码不写本页，构建失败）。上线前核对项见 `launch-checklist.md`。

## 值班与分级

| 级别 | 含义 | 响应 |
|------|------|------|
| 严重（`CRITICAL`） | 买家已付款拿不到卡 / 敏感数据解不开 / 库满 / 告警本身失灵 | 立即处理；30 分钟内无进展升级给负责人 |
| 注意（`WARN`） | 积压、滞后、对账未做、阈值逼近 | 当班内处理；跨班交接写明 |

- 看哪里：后台「旅行卡 › 运维 › 运营告警」看当前快照；「运维概览」看库容量、各类积压、数据密钥版本。
- 推送：worker 进程（只在 manager-api，`LIROAM_WORKER_ENABLED=true`）每 5 分钟把每条告警写一行 WARN 日志 `运维告警[级别][编码] 标题 ×数量：说明`。日志平台按关键字 `运维告警[` 配推送，`[CRITICAL]` 走电话 / 加急，`[WARN]` 走群消息。值班通道（群、电话、轮值表）【待用户提供】。
- 阈值：全部是设置项 `alert.*`（`lr_setting`，后台改即生效），默认值见下表各条；上线后按业务量复核。

## 告警处置

### `ALERT_SOURCE_FAILED` 告警检查失败（严重）
某个告警来源查询异常，等于这块监控失明。看 manager-api 日志里同时间的异常栈（多为库连不上、表锁、SQL 超时）；库正常后下一轮巡检自动消失。持续出现按「数据库」排查。

### `COMMAND_MANUAL` 供应商指令转人工（严重）
重试用尽或结果不明（写后超时）的开卡 / 加包 / 停复机指令已转「卡与履约 › 人工待办」。先在供应商后台查该卡真实状态，再在人工待办按实际结果处理（已开通 → 标成功；未开通 → 重新发起或退款）。批量出现按「供应商故障」处置。

### `COMMAND_RETRYING` 供应商指令反复失败（注意，`alert.command_retry_attempts` 默认 3 次）
指令仍在自动重试。少量：观察；同一供应商大量：按「供应商故障」处置。

### `RATE_LIMITED` 供应商限流频繁（注意，`alert.rate_limited_per_hour` 默认 20 次/时）
本地令牌桶在推迟指令，买家交付会变慢。确认供应商给的 QPS 是否下调；大促前与供应商申请提额。

### `MANUAL_BACKLOG` 人工待办积压（注意，`alert.manual_backlog` 默认 20 条 / `alert.manual_task_age` 24 小时）
「人工待办」按创建时间从早到晚处理；超龄的优先。积压原因集中在某一类时找对应条目。

### `CREDENTIAL_TIMEOUT` 卡开通后长时间未交码（严重）
买家已付款但没拿到激活码 / 物流。在「卡台账」找到该卡：池卡 / 导入交码的补录交码内容，实体卡录物流；供应商侧未出码则联系供应商，必要时退款。

### `POLL_LAG` 用量查询滞后（注意，`alert.poll_lag` 默认 30 分钟）
worker 没跟上或供应商查询接口慢。看 manager-api 是否存活、worker 日志有无异常、是否同时有 `RATE_LIMITED`；只影响用量展示，不影响交付。

### `SHELL_DELIVERY_FAILING` 壳订单发货回写失败（注意，`alert.shell_delivery_attempts` 默认 3 次）
卡已交付但商城订单没置为已发货，买家端订单状态不对。看 manager-api 日志中壳发货异常（订单状态被改、物流公司未启用等），修正后等补偿任务重试；仍失败在商城后台手工发货。

### `FX_STALE` 汇率过期（注意）
汇率同步失败超过设置时长。「定价 › 定价与汇率」看来源与最近同步；手工同步一次，来源故障时暂停调价确认。

### `REPRICE_PENDING` 调价建议待确认（注意）
汇率或资费变动后出了新建议。在「定价 › 调价」逐条确认或驳回。

### `REPRICE_BACKLOG` 调价建议积压（注意，`alert.reprice_pending_age` 默认 24 小时）
同上，已超时未处理，售价可能低于成本，优先看毛利率最低的。

### `AGENT_NEGATIVE_BALANCE` 代理佣金余额为负（注意）
已提现后发生退款冲正，后续佣金会先抵扣。金额大或长期不回正时联系该分销员线下追回，结果记在「佣金与提现」。

### `WITHDRAWAL_BACKLOG` 提现申请积压（注意）
「佣金 › 佣金与提现」审批或登记打款。

### `PAYMENT_RECON_MISSING` 昨日支付对账未做（注意）
在「报表与对账 › 日对账」导入昨日支付渠道账单（CSV 列 `order_sn,trade_no,amount`）。

### `RECON_DIFF_OPEN` 对账差异待处理（注意）
「日对账」逐条看差异（支付 / 供应商 / 渠道），查明后标已处理或忽略并写原因。

### `DB_CAPACITY` 数据库占用接近容量（≥80% 注意，≥100% 严重；`alert.db_capacity_mb` 默认 20480 MB，设 0 不检查）
「运维概览」看最大的表。先确认是否异常增长（日志表、重复导入）；再扩容磁盘 / 实例或归档历史数据。扩容后同步检查备份存储空间。阈值按实例实际配额改。

### `DATA_KEY_UNREADABLE` 敏感数据解不开（严重）
库里有行的 `key_version` 在当前进程没有对应密钥 `LIROAM_DATA_KEY_Vn`（告警说明里写了缺哪个版本）。多为下线旧密钥前没重加密完，或新进程漏配密钥。立刻把该版本密钥补回密钥管理并重启后端；不要再写入。见「数据密钥轮换」。

### `DATA_KEY_STALE` 敏感数据仍用旧密钥版本（注意）
轮换后还有旧版本数据。在「运维概览 › 数据密钥」分批「重加密一批」直到待重加密为 0，再按流程下线旧版本。

## 积压一览（「运维概览」）

| 编码 | 含义 | 去哪处理 |
|------|------|----------|
| `SUPPLIER_COMMANDS` | 未完成的供应商指令 | 正常在流转；持续增长按「供应商故障」 |
| `MANUAL_TASKS` | 未处理人工待办 | 卡与履约 › 人工待办 |
| `SHELL_DELIVERIES` | 待回写商城发货 | 见 `SHELL_DELIVERY_FAILING` |
| `CHANNEL_WRITEBACKS` | 回传失败或转人工的渠道单 | 渠道 › 渠道订单（转人工的按渠道后台实际状态处理） |
| `RECON_DIFFS` | 未处理的对账差异 | 报表与对账 › 日对账 |

## 场景手册

### 供应商故障
1. 判断范围：告警 `COMMAND_RETRYING` / `COMMAND_MANUAL` / `RATE_LIMITED` 是否集中在同一供应商；「运维概览」`SUPPLIER_COMMANDS` 是否持续增长。
2. 联系供应商确认故障与预计恢复时间；期间指令自动退避重试，不需要手工重发。
3. 长时间不可用：在「旅行卡商品」下架该供应商的 SKU，避免继续收单。
4. 恢复后：积压指令自动消化；`COMMAND_MANUAL` 转人工的逐条按供应商后台实际状态处理；已付款超时未交付的主动联系买家或退款。
5. 演练（本机）：`POST /manager/liroam/dev/mock-upstream/faults` `{"adapterKey":"mock-shape-a","operation":"PROVISION","failure":"CONNECT_FAILED","count":5}` 让模拟供应商接下来 5 次开卡失败；买一张该供应商的卡观察告警与恢复；`/faults/clear` 清除。只在 dev/test 装配。

### 数据库备份与恢复
- 生产：全量备份 + binlog 增量，保留期与存放位置【待用户提供】；上线前在隔离库做一次恢复演练（上线清单 #13）。
- 本机：`node scripts/dev.mjs backup` 写 `temp/backups/lilishop-<UTC时间>.sql.gz`；`node scripts/dev.mjs restore-drill` 恢复到临时库 `lilishop_restore_drill`，逐表行数与触发器数比对后删除临时库，输出用时。
- 真恢复：停后端 → 恢复到新库并核对 → 改连接指向新库 → 起后端 → 看「运营告警」「运维概览」与一张卡的买家「我的卡」。迁移只增不改，应用版本可回退到旧库（上线清单 #14）。

### 数据密钥轮换（敏感字段 AES-GCM，`LIROAM_DATA_KEY_V1..V32`）
新写入用最大版本，旧版本只解密；查重 HMAC 密钥 `LIROAM_DATA_HASH_KEY` 不轮换。加密列登记在 `liroam-schema` 的 `SealedTables`（新加 `*_cipher` 列不登记测试失败）。
1. 新增：在密钥管理加 `LIROAM_DATA_KEY_V(n+1)`（32 字节随机，base64），滚动重启全部后端。本机：`node scripts/dev.mjs rotate-data-key` 再 `up --ui=none`。
2. 重加密：「运维概览 › 数据密钥」点「重加密一批」（每批 1–1000 行，乐观更新，可重复、可中断），直到待重加密为 0；出现 `DATA_KEY_STALE` 即未完成。
3. 下线旧版本：确认所有表都没有该版本的行后，从密钥管理删除旧版本并重启。本机：`node scripts/dev.mjs retire-data-key <n>`（有剩余行或是当前版本会拒绝）。
4. 复核：「运维概览」无「无法解密」行；买家「我的卡」能看到激活码。出现 `DATA_KEY_UNREADABLE` 按该条处置。
- 密钥泄露：同上流程立即执行，重加密完成前不下线；同时排查泄露途径。生产密钥管理系统与审批流程【待用户提供】。

### 新渠道接入
渠道只经 `ChannelAdapter`（拉单 / 回传 / 日对账单）接入，业务代码不改：
1. 新模块 `modules/liroam-channel-<名字>`：实现适配器，bean 名 = `lr_channel.adapter_key`；渠道名只许出现在本模块（`VendorNameScanTest` 登记名字）。
2. 本机先做模拟实现：继承 `liroam-channel-mock` 的 `SimulatedChannel`，只写该渠道报文形状；后台「渠道订单」的模拟面板自动出现，可造单 / 改对账 / 注入回传失败。
3. 后台「渠道与 SKU 映射」加渠道与映射；走通 拉单 → 出卡 → 回传 → 买家认领到「我的卡」 → 日对账。
4. 真适配器拿到资质、密钥、报文样例后替换，`adapter_key` 切过去即可。现有：京东 `mock-jd`、小红书 `mock-xhs`（均只模拟，真实字段【待核实】）。
